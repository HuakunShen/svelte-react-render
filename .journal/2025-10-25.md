# 2025-10-25: Self-Contained Plugin Workers Architecture

## Core Decision: Plugin Workers as Standalone Bundles

### Problem Context

The initial design had a centralized `react-plugin.worker.ts` that dynamically loaded plugin code. This approach had several issues:

- Plugin code had to rely on external dependencies (React, API) being provided
- Complex import transformation logic was needed to map imports to globals
- Multiple React instances could cause "Invalid hook call" errors
- Unclear separation between worker infrastructure and plugin code

### Options Considered

**Option 1: Global Dependencies with Import Transformation**

- Expose React and API as globals in the worker
- Transform plugin imports to use these globals
- Pros: Smaller plugin bundles
- Cons: Complex build process, fragile import mapping, hard to debug

**Option 2: Self-Contained Plugin Workers**

- Each plugin is a complete worker script
- Bundle everything: kkrpc, React, API, and plugin code
- Plugin handles its own RPC setup and initialization
- Pros: Simple, portable, no dependency coordination needed
- Cons: Larger file sizes (but acceptable for modern web)

### Final Decision & Rationale

**Chose Option 2: Self-Contained Plugin Workers**

Key reasons:

1. **Simplicity**: Each plugin is a standalone ES module that can be served from any URL
2. **Portability**: Plugins are truly external - can be developed, built, and hosted independently
3. **Reliability**: No risk of version mismatches or multiple React instances
4. **Realistic**: Matches real-world plugin architecture (like Raycast, VSCode extensions)
5. **Developer Experience**: Easier to understand and debug

### Architecture Changes

#### Before

```
Main Thread                    Worker Thread
-----------                    -------------
WorkerPluginHost.svelte   <->  react-plugin.worker.ts
ComponentRenderer.svelte  <-   (loads plugin via import())
RPC: renderPlugin(url)    ->   Dynamic plugin loading
```

#### After

```
Main Thread                    Plugin Worker (Self-Contained)
-----------                    ------------------------------
WorkerPluginHost.svelte   <->  simple-demo.worker.ts
  - fetch(pluginUrl)             - kkrpc bundled
  - Blob + Worker creation       - React bundled
  - RPC connection               - API bundled
ComponentRenderer.svelte  <-     - RPC setup
                                 - Auto-initialization
```

### Key Changes Made

**1. Plugin Package Structure (`packages/plugin-example/`)**

- Moved both demos from `demo-sveltekit` to `plugin-example`
- Created separate worker scripts: `simple-demo.worker.ts`, `advanced-demo.worker.ts`
- Each worker bundles everything (no externals)
- Copied serialization utilities for independence
- Exported components for main-thread mode reuse

**2. Build System (`build.ts`)**

- Builds both plugins as complete ES modules
- Single HTTP server on port 3000 serves both
- Outputs: `dist/simple-demo.js` and `dist/advanced-demo.js`
- Auto-rebuild on file changes in dev mode

**3. WorkerPluginHost (Redesigned)**

- Fetches plugin script via `fetch()`
- Creates blob worker: `Blob([script]) -> Worker(URL.createObjectURL(blob))`
- No more `renderPlugin()` - plugins auto-initialize
- Clean RPC connection pattern

**4. Dual-Mode Support (Restored)**

- Worker mode: Loads external plugin bundles
- Main-thread mode: Imports components directly from `plugin-example` package
- Both modes share the same React component code
- Easy comparison of performance and architecture

**5. Cleanup**

- Deleted `react-plugin.worker.ts` (replaced by self-contained plugins)
- Removed internal demo files (moved to plugin-example)

### Technical Implementation Details

#### Worker RPC Pattern (Following kkRPC Best Practices)

```typescript
// Separate initialization logic from RPC expose
async function initializePlugin(props?: any) {
  // Setup renderer, bridge, subscribe to updates
}

function setupRPC() {
  rpcChannel = new RPCChannel<WorkerAPI, MainThreadAPI>(io, {
    expose: {
      async initialize(props?: any) {
        return initializePlugin(props);
      },
      // ... other methods
    },
  });
}

// Initialize RPC then auto-initialize plugin
setupRPC();
initializePlugin();
```

**Important**: Cannot call own exposed methods directly. Expose methods are for the other side to call via `getAPI()`.

#### Blob Worker Creation

```typescript
const response = await fetch(pluginUrl);
const scriptText = await response.text();
const blob = new Blob([scriptText], { type: "application/javascript" });
const blobURL = URL.createObjectURL(blob);
const worker = new Worker(blobURL);
URL.revokeObjectURL(blobURL); // Clean up after worker created
```

## 2025-10-25 05:20: Node.js WebSocket Integration for Plugin System

### Core Decision/Topic
Successfully implemented Node.js WebSocket integration to run React plugins, achieving a Raycast-like architecture where plugins run in Node.js and communicate with the browser UI via WebSocket RPC.

### Options Considered
1. **Web Worker Only**: Continue with existing Web Worker architecture only
2. **Direct Node.js Integration**: Use Node.js APIs directly in browser (not feasible)
3. **WebSocket Bridge**: Implement Node.js servers with WebSocket communication
4. **HTTP API Bridge**: Use HTTP requests instead of WebSockets
5. **Shared Memory**: Use shared memory buffers (complex implementation)

### Final Decision & Rationale
Chose WebSocket bridge architecture because:
- **Security**: Plugins run in isolated Node.js process, not in browser context
- **Performance**: Near real-time communication with minimal latency
- **Raycast-like**: Mirrors successful architecture used by Raycast plugin system
- **Flexibility**: Can run Node.js-specific APIs (file system, network, etc.)
- **Scalability**: Multiple plugin servers can run simultaneously on different ports
- **Shared Logic**: 95% of plugin code can be reused between Web Worker and Node.js environments

### Key Changes Made

#### 1. Shared Plugin Runtime (`packages/plugin-example/src/shared-plugin-runtime.ts`)
- Extracted common plugin logic into reusable functions
- Created `PluginRuntimeState` interface for managing plugin state
- Implemented shared initialization, props updates, and handler execution
- Created `createPluginAPI` factory function for both environments
- Maintains same component serialization and event handling patterns

#### 2. Node.js WebSocket Servers
- **Simple Demo Server** (`simple-demo.server.ts`): Runs on port 3001
- **Advanced Demo Server** (`advanced-demo.server.ts`): Runs on port 3002
- Both use `ws` library and `kkrpc` for WebSocket communication
- Proper connection handling with cleanup and graceful shutdown
- Each connection gets isolated plugin runtime state

#### 3. Browser WebSocket Client (`WebSocketPluginHost.svelte`)
- Svelte 5 component using proper runes (`$state`, `$effect`, `$props`)
- Automatic connection management with reconnection logic
- Error handling and loading states
- Props synchronization between browser and server
- Integration with existing `ComponentRenderer` component

#### 4. Demo Application Integration (`+page.svelte`)
- Added third runtime mode "🖥️ Node.js" alongside existing modes
- New server URL routing based on demo type
- Updated UI to show WebSocket URLs in window chrome
- Added server startup scripts to package.json

#### 5. Package Scripts (`plugin-example/package.json`)
- `server:simple`: Start simple demo server
- `server:advanced`: Start advanced demo server
- `server`: Start both servers concurrently
- Added `ws` and `@types/ws` dependencies

### Technical Implementation Details

#### Architecture Flow
```
Browser (Svelte) ↔ WebSocket ↔ Node.js Server ↔ React Plugin ↔ Svelte UI
```

#### RPC Communication
- Uses `kkrpc` library for type-safe RPC over WebSockets
- Client calls server's `initialize()` method on connection
- Server sends serialized component trees via `updateComponentTree()`
- Event handlers registered by ID and executed via `executeHandler()`

#### Component Serialization
- Identical serialization logic as Web Worker mode
- Component trees serialized to JSON format
- Event handlers mapped to string IDs for RPC transport
- Svelte `ComponentRenderer` unchanged, works with both modes

#### Error Handling & Reconnection
- Automatic reconnection with exponential backoff
- Maximum 5 reconnection attempts with manual retry option
- Proper cleanup on component destruction and connection close
- Error states displayed to user with retry options

#### Svelte 5 Compliance
- Fixed all component syntax to use Svelte 5 runes
- `$state()` for reactive state management
- `$effect()` for side effects and watchers
- `$props()` for component properties
- Proper component lifecycle management
