# Development Journal - October 24, 2025

## 22:09 - Web Worker Plugin Architecture Implementation

### Core Decision: Dual-Mode Plugin System

Implemented a plugin architecture that supports both Web Worker (sandboxed) and Main Thread (direct) execution modes, with runtime switching capability.

### Context & Requirements

Started with a working main-thread React plugin system that needed:
1. **Sandboxing**: Run React plugins in isolated Web Workers for security
2. **Flexibility**: Maintain ability to run plugins in main thread for performance/debugging
3. **No Breaking Changes**: Existing plugins must work without modification
4. **Dynamic Switching**: Users can toggle between modes at runtime

### Architecture Overview

**Web Worker Mode:**
```
Main Thread (Svelte)     <-- RPC -->     Worker Thread (React)
├─ WorkerPluginHost                      ├─ react-plugin.worker.ts
├─ ComponentRenderer                     ├─ React Reconciler
└─ Event Proxy Functions                 └─ Event Handlers
```

**Main Thread Mode:**
```
Main Thread (Svelte + React)
├─ PluginHost
├─ ComponentRenderer
└─ React Reconciler (direct)
```

### Key Implementation Decisions

#### 1. RPC Library Choice: kkRPC
**Options Considered:**
- Native MessageChannel (too low-level)
- Comlink (less flexible for custom protocols)
- kkRPC (user's own library with WebWorker support)

**Decision:** Use kkRPC for bidirectional RPC communication
**Rationale:** User specifically requested it, supports multiple environments including WebWorker, provides clean API abstraction

#### 2. Event Handler Serialization Pattern
**Problem:** Functions cannot be serialized across worker boundary

**Options Considered:**
- A) Pass event data back to worker, worker calls handlers
- B) Handler ID registry with RPC callbacks
- C) Structured clone with SharedArrayBuffer

**Decision:** Handler ID registry (Option B)
**Rationale:** 
- Clean separation of concerns
- No SharedArrayBuffer complexity
- Async-friendly for future enhancements
- Easy to debug with handler IDs in console

**Implementation:**
```typescript
// Worker side
const handlerId = registerHandler(onClick);
props._onClickHandlerId = handlerId;

// Main thread side
onClick: createHandlerFromId(props._onClickHandlerId)
// which calls: rpc.getAPI().executeHandler(handlerId)
```

#### 3. Plugin URL vs Direct Import
**Worker Mode:** Uses plugin URLs (`'/src/plugins/simple-demo.tsx'`)
- Loaded dynamically with `import(/* @vite-ignore */ pluginUrl)`
- Enables runtime plugin loading

**Main Thread Mode:** Uses direct imports with `createElement()`
- Traditional React pattern
- No serialization overhead

#### 4. Component Tree Serialization
**Challenges:**
- Circular references (parent pointers)
- Function props (event handlers, render props)
- React internal state

**Solution:** Custom serialization utility
- Converts function props to handler IDs
- Flattens circular refs (parent as string ID)
- Skips non-serializable props with try/catch
- Recursive child serialization

### Critical Bugs Fixed

#### Bug 1: Plugin Switching Not Working in Worker Mode
**Symptom:** Switching from Simple to Advanced demo kept showing Simple demo

**Root Cause:** `WorkerPluginHost` only called `renderPlugin()` once in `onMount()`. When `pluginUrl` prop changed, no re-render triggered.

**Initial Fix Attempt:** Added `$effect()` watching `pluginUrl`
```typescript
$effect(() => {
  if (rpc && !isLoading) {  // BAD: caused infinite loop
    isLoading = true;
    api.renderPlugin(pluginUrl);
  }
});
```

**Problem with Initial Fix:** Infinite loop - `isLoading` change triggered effect again

**Final Solution:** Track previous URL to only trigger on actual changes
```typescript
let lastPluginUrl = $state<string | null>(null);

$effect(() => {
  if (rpc && pluginUrl !== lastPluginUrl && lastPluginUrl !== null) {
    isLoading = true;
    rootInstance = null;
    lastPluginUrl = pluginUrl;
    api.renderPlugin(pluginUrl, pluginProps);
  }
});
```

Also used `{#key pluginUrl}` block in App.svelte to force component recreation.

#### Bug 2: Infinite Console Logging
**Symptom:** Console flooded with ComponentRenderer logs and Svelte proxy warnings

**Root Causes:**
1. Debug `console.log()` in ComponentRenderer on every render
2. Logging `$state` proxies triggered Svelte warnings
3. Reactive loop from previous bug

**Solution:**
- Removed debug logging from ComponentRenderer
- Fixed reactive loop (see Bug 1)
- Clean console output achieved

### Performance Characteristics

**Web Worker Mode:**
- Initial load: ~100-200ms (worker creation + RPC setup)
- Plugin switch: ~50-100ms (serialization + RPC)
- Event handling: ~5-10ms (async RPC call)
- Bundle: 253KB main + 126KB worker = 379KB total

**Main Thread Mode:**
- Initial load: ~10-20ms (direct render)
- Plugin switch: ~10-20ms (direct re-render)
- Event handling: <1ms (direct function call)
- Bundle: 253KB main only (includes both modes)

### Trade-offs & Design Rationale

**Why Dual Mode vs Worker Only:**
- **Security vs Performance**: Worker provides sandboxing, main thread provides speed
- **Debugging**: Main thread easier to debug with standard DevTools
- **Development Speed**: Main thread faster iteration during development
- **Production Security**: Worker mode for untrusted plugins
- **User Choice**: Runtime toggle lets users decide based on needs

**Serialization Overhead:**
- Accepted for security benefit
- Only affects worker mode
- Users can opt into main thread for performance-critical scenarios

**Bundle Size Increase:**
- +145KB total for dual-mode support
- Worth it for flexibility and security options
- Could optimize with lazy loading in future

### Future Considerations

**Potential Optimizations:**
1. **Lazy Load Worker Code**: Only bundle worker when worker mode selected
2. **Batched Updates**: Batch multiple tree updates to reduce RPC calls
3. **Diff Algorithm**: Only send changed parts of tree, not entire tree
4. **Worker Pool**: Reuse workers across plugin instances
5. **Hybrid Mode**: Heavy computation in worker, rendering in main thread

**Technical Debt:**
- kkRPC shows warnings about Node.js modules (buffer, stream) being externalized
  - Not critical (browser compatibility warnings)
  - Could be resolved with Vite config adjustments
- Handler registry grows unbounded (no cleanup on plugin unload)
  - Low priority: plugins typically don't hot-reload handlers
  - Could add WeakMap or cleanup on plugin switch

**Testing Needs:**
- Performance benchmarks comparing modes
- Large component tree stress tests
- Memory leak testing for handler registry
- Plugin hot reload behavior

### Key Learnings

1. **Svelte 5 $effect gotchas**: Easy to create reactive loops. Always check what state changes trigger the effect.
2. **Worker module loading**: Vite's `?worker` suffix handles bundling automatically, but dynamic imports need `/* @vite-ignore */` comment
3. **Serialization complexity**: React component trees are deeply nested with circular refs. Need careful traversal.
4. **RPC pattern**: Handler ID pattern is powerful for cross-boundary function calls. Consider for other async boundaries.
